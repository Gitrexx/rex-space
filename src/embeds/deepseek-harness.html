Agent infrastructure · Coding agents · Runtimes

DeepSeek Harness (dsh)

You want to know what dsh actually is, which problem it solves, how it differs from Claude Code, Codex, OpenCode and the SDK frameworks, when it is the right pick, and what building and deploying an agent on it looks like in code. This module covers all of that against the state of the project as of early September 2026, ten days after its developer preview.

Full mode — deep-dive blocks visible

The one idea

A harness is everything around the model that turns a chat completion into an agent: the loop that decides when to call the model again, the tool registry, the shell and file editor, the session transcript, the sandbox, the permission prompts, the UI. Claude Code, Codex CLI and OpenCode are harnesses with a model attached. They each ship one fixed arrangement of those parts.

DeepSeek Harness (the CLI is dsh) is DeepSeek's answer to the question "what if none of those parts were fixed?" It is an MIT-licensed runtime, released as a developer preview on 13 August 2026, in which every capability is a plugin: the model adapter, the tool registry, the session log, the sandbox, the scheduler, the web UI, and the agent loop itself. There is no privileged core to patch. You compose an agent from plugins in configuration, and you swap any piece without forking the source.

Key insight

dsh is not "DeepSeek's Claude Code". It is a runtime for building agents like Claude Code, and it can even run Claude Code and Codex as sub-agents inside a loop you own. Judge it as infrastructure, not as a finished assistant.

Two principles from the launch page summarise the design: everything is a plugin, and every run is traceable. The second one matters as much as the first: dsh keeps an append-only session log with the invariant that anything the model saw must be reconstructible from the log, which is what makes resume, fork and replay first-class.

What problem it solves

Three pressures pushed the industry toward this shape of tool, and dsh is the first vendor-backed harness to embrace all three at once.

1. The harness moves results more than the model does

Winder.ai's 2026 harness survey cites a study where changing only the harness lifted a Terminal-Bench score from 52.8% to 66.5% with the same model. Community benchmarking after DeepSeek V4 launched found up to a 7× cost difference between harnesses running the same DeepSeek model. If the loop, the prompt budget and the compaction strategy decide that much, engineers want to control them. DeepSeek's own V4-Pro agent numbers were measured with dsh in minimal mode, which tells you they think of the harness as part of the measured system.

2. Monolithic harnesses lock you in twice

Claude Code and Codex lock you to a model vendor and to their loop. OpenCode and OpenHands free the model but still hand you a fixed core with extension points around the edges. If you want a different compaction policy, a different tool-approval flow, or an agent that writes programs instead of issuing tool calls, you fork. dsh moves those decisions into configuration.

3. Long-running agents need to be inspectable and resumable

A 16-hour autonomous run is only useful if you can see what happened, resume it after a crash, and fork it from the point where it went wrong. dsh's append-only event log captures user messages, tool invocations, reasoning states, token metrics and sub-agent dispatches into one trajectory, and everything else (transcripts, forks, resumes, telemetry, persistence) is derived from that stream.

Deep dive — the Cordis theory underneath

dsh is built on Cordis, a plugin meta-framework from the same authors, described in the arXiv paper A Programming Paradigm for Spatiotemporal Composability (2608.25512). The paper names two properties a plugin system needs to be safely reconfigurable at runtime:

  • Temporal composability: removing a component completely reverts its side effects. Every registration a plugin makes (a tool, an event listener, a service, a timer) is a revertible effect that carries its own inverse, so unloading is exact.
  • Spatial composability: components declare what they depend on, and the kernel reacts. A plugin that injects the tools service loads only once that service exists, unloads automatically if the service disappears, and reloads when it returns.

The paper explicitly motivates this with "self-evolving agent harnesses": a runtime where the agent can add, remove or rewrite its own capabilities while running. dsh's cordis preset (marketed as "Creator" mode) is exactly that: the model writes JavaScript against the live runtime. The theory is what makes that safe enough to ship.

How it is put together

Read the architecture as four layers, bottom-up.

Kernel: Cordis

The kernel does one job: mount and unmount plugins, resolve their dependencies, and route services and typed events between them. Each plugin runs in a fiber with a small state machine (pending → loading → active → unloading → disposed). It knows nothing about agents.

Plugins: the capability families

Composition: bundles → profiles → patches → presets

  • Bundles are ordered sets of plugins. dsh-base provides the core services; dsh-web-app or dsh-headless stack on top.
  • Profiles live at $DSH_HOME/profiles/<name> and combine bundles with environment-specific config. Five ship: web, headless, sdk, sdk-minimal, acp. Each profile folder holds a package.json (plugin dependencies), a dsh.profile (bundle order and lifecycle) and a cordis.patch.yml.
  • Patches (cordis.patch.yml, or --patch file.yml at launch) insert, remove or override plugins without touching the originals. Layers cascade: bundle defaults, then profile, then home-level, then launch-time.
  • Agent presets are per-session YAML personas mounted into their own fiber: system prompt, tool selection, model parameters. Four ship:

The session log

Two units of time: a step is one model request plus the tool calls it produced; a turn is zero or more steps, opened before the first input and closed when the agent's obligations are met. Every event is appended, never edited. The on-disk format is at version 0 and the backends reject older formats with no migration path, which is the single biggest reason not to run production sessions on it yet.

One turn moving through the plugin pipeline. Each hop lights the plugin that owns it and appends an event to the session log at the bottom. Press Swap LLM adapter mid-run: the kernel unloads the old adapter fiber, loads the new one, and the loop carries on with the same log. That is temporal composability in one click.

Deep dive — the tool execution pipeline and its extension points

A tool call is not a function call. It passes through a pipeline, and each stage is an event other plugins can hook:

  1. tools/pre-execute: an extensible allow / deny / ask policy. This is where permission plugins live, and where a third-party policy-control plugin (one appeared on day three of the preview) inserts itself.
  2. ctx.tools.guard(): a final, monotonic deny. Guards can only remove permission, never add it.
  3. tools/execute: the call itself, wrappable with deadlines, retries or metrics.
  4. tools/post-execute: replace the presentation or attach context before the result reaches the model.
  5. tools/result: observe the immutable, normalised outcome.

Arguments are frozen as immutable JSON before execute runs, and the registry validates the returned value against the tool's declared output.schema. In a headless composition, an ask outcome resolves to deny: an unattended agent cannot approve itself.

dsh states the invariant "model-visible means logged." What does that commit the runtime to?

  • Every model response is logged so the UI can show it later.
  • Anything that reaches a model request must be reconstructible from the append-only event log, so resume, fork and replay can rebuild the exact context.
  • The model can read its own session log as a tool.
The invariant is about the input side, not display. If some plugin injected text into the prompt without logging it, a resumed or forked session would see a different context than the original run. Making the log the only source of model-visible state is what lets transcripts, forks and telemetry all be derived views of one stream.

The useful cut is not "open vs closed" but "is the loop yours?" Most tools give you a finished agent with hooks around the edges. dsh gives you the parts.

Positioning in one line

Several reviewers converge on the same verdict: OpenCode is the safer daily driver in 2026; dsh is the more consequential architecture. Pick by which of those two you need this quarter.

Deep dive — dsh as a layer above Claude Code and Codex

The subagent family ships seven providers. Two are named integrations: subagent-claude-code delegates to the Claude Agent SDK inside the parent's workspace, and subagent-codex talks to codex app-server --stdio. The rest are generic: any Agent Client Protocol agent, a peer dsh over stdio JSON-RPC, and in-process children with or without the parent's history seeded in. Sub-agents behave like contractors: they receive a self-contained task, work alone, and return only a final answer (the Claude Code provider sets inheritsParentContext: false). Since the v0.1.2 alphas, parent and child can also exchange messages mid-task via send_message, and children are continuable with message queueing.

The practical consequence: you can run the same task through DeepSeek V4, Claude Code and Codex side by side under one orchestrator, one log format and one permission policy. That is a genuinely new capability for an evaluation team.

A team wants a self-hosted coding agent for daily use on open-weight models, and they need it to be stable across upgrades for the next six months. Which is the better fit today?

  • DeepSeek Harness, because it is model-agnostic and MIT-licensed.
  • OpenCode, because it is model-agnostic, self-hosted and stable, while dsh is a preview with a version-0 session format that breaks between releases.
  • Claude Code, because it is the most mature harness.
Model-agnostic and MIT apply to both OpenCode and dsh, so they do not decide it. Stability across upgrades does: dsh explicitly warns of compatibility-breaking changes, and its session backends reject old on-disk formats with no migration. Claude Code fails the open-weight requirement outright. Revisit dsh once the session format and plugin contracts stabilise.

When to use it, and when not to

Good fits

  • Building an agent product where the loop, approval flow, compaction or tool set must be yours, and you would otherwise fork a harness.
  • An evaluation rig that runs the same task across DeepSeek, Claude Code and Codex under one log format. One install, seven sub-agent providers.
  • Long-running headless jobs where a small system prompt, default auto-compaction and a resumable log matter more than a polished TUI.
  • Harness research: benchmarking what the harness contributes, in minimal mode, is exactly what DeepSeek did for V4-Pro.
  • Cost-sensitive DeepSeek workloads. Even after the August 2026 price rise (V4-Pro at $0.66 / $1.98 per million tokens off-peak, double at peak), DeepSeek stays far below Claude Opus and OpenAI flagship pricing, and dsh is the first-party harness for it.

Poor fits, for now

  • Production sessions that must survive upgrades. Session format version 0, no migration path, weekly breaking changes.
  • Anything needing network isolation. The sandbox governs filesystem effects only. Network and process visibility are outside its vocabulary, in every mode.
  • A finished assistant today. If you want a TUI that just works, OpenCode or Claude Code will cost you less time.
  • Python-native typed agents. The Python SDK drives dsh as a subprocess over JSON-RPC. If you want the agent to be Python, Pydantic AI or a vendor SDK is the natural home.
  • Explicit multi-agent graphs. dsh has sub-agents and a workflow engine, but a stateful graph with branches and human checkpoints is still LangGraph territory. The two can stack.

Hands-on: install and run

Requirements are Node ^22.19.0 || >=24.0.0 and pnpm for source builds. The fastest path is the npm package.

# Web UI on http://127.0.0.1:3080 (add --no-open to skip the browser)
export DEEPSEEK_API_KEY=sk-...
npx @deepseek-ai/dsh web

# or install globally and pin the version (breaking changes are weekly)
npm install -g @deepseek-ai/dsh@0.1.3-alpha.2
dsh web

# from source
git clone https://github.com/deepseek-ai/deepseek-harness.git
cd deepseek-harness && pnpm install && pnpm run build
pnpm dsh web

The CLI is really a profile launcher. The profile decides which bundles boot and how the process talks to the outside world:

dsh --profile web                       # browser UI (dsh web is an alias)
dsh --profile headless "summarize this workspace"
                                        # one fresh persisted session, prints the answer, exits
dsh --profile sdk                       # serve SDK clients over JSON-RPC on stdio
dsh --profile sdk-minimal               # same, with the standalone minimal agent tree
dsh --profile acp                       # serve Agent Client Protocol clients (editors, automation)
dsh --profile web --patch ./my.cordis.yml   # apply a config overlay for this launch
dsh --profile web --dump-config         # print the composed plugin tree without booting
dsh plugin --profile web add <pkg>     # manage a profile's plugins (forwards to pnpm)

Pointing it at other models

Settings live in $DSH_HOME/settings.yaml; credentials in $DSH_HOME/.credentials.yaml and are write-only from the UI. Catalog providers (Anthropic, OpenAI, Bedrock, Vertex, Azure, Codex) are added under Settings → Models. A custom OpenAI-compatible gateway or a self-hosted vLLM/SGLang server is declared under the llm-pi-ai plugin:

# $DSH_HOME/settings.yaml (excerpt)
llm-pi-ai:
  providers:
    my-gateway:                       # lowercase provider id, permanent once created
      apiKeyEnv: GATEWAY_API_KEY
      api: openai-completions
      baseURL: https://gateway.example/v1
      models:
        - id: qwen3-coder
        - id: vision-preview
          input: [text, image]        # declare modalities per model
      # compat: { supportsDeveloperRole: false, maxTokensField: max_tokens }

"Fetch available models" queries the endpoint's /models route, so a local vLLM server is discoverable without hand-listing models.

Building on it: your first plugin and tool

A plugin is a TypeScript module with a name and an apply(ctx). Everything registered through ctx is a reversible effect, so there is no teardown code to write for listeners, tools or timers.

// src/greet-tool.ts
import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'greet-tool'
export const inject = ['tools']          // load only once the tool registry exists

export function apply(ctx: Context) {
  ctx.tools.register(defineTool({
    name: 'greet',
    description: 'Greet someone by name.',
    parameters: {
      name: { type: 'string', required: true, description: 'The name to greet' },
    },
    output: {
      schema: { type: 'string' },                       // canonical value the tool returns
      render: (_args, value) => [{ type: 'text', text: value }],   // model-facing content
    },
    async execute(args, exec) {
      // exec.signal fires on cancellation; honour it for long work
      return `Hello, ${args.name}!`
    },
  }))

  // explicit cleanup for things ctx does not own (sockets, timers)
  ctx.effect(() => {
    const timer = setInterval(() => ctx.logger?.info?.('tick'), 5000)
    return () => clearInterval(timer)
  })
}

Register it with a patch and launch:

# cordis.yml
- insert:
    - id: greet
      name: '/absolute/path/to/src/greet-tool.ts'
pnpm dsh web --patch ./cordis.yml

Three things to notice. The framework validates model-generated arguments against parameters before execute runs, so you never parse JSON. The return value is validated against output.schema and then passed to render; UI-only formatting stays out of the model result (there are separate pure presentCall / presentResult hooks for cards). And because registration is effect-based, disposing the plugin fiber unregisters the tool, which is what hot reload (@deepseek-ai/cordis-plugin-hmr) relies on.

Adding a policy hook

// deny any shell command that touches production credentials
export const name = 'no-prod-secrets'
export const inject = ['tools']
export function apply(ctx: Context) {
  ctx.on('tools/pre-execute', (call) => {
    if (call.name === 'bash' && /PROD_|\.aws\/credentials/.test(String(call.arguments.command)))
      return { decision: 'deny', reason: 'blocked by no-prod-secrets' }
  })
}

The event name and the pre-execute stage are documented; the exact shape of the handler's return value is from the preview docs and may change, so check the tool-authoring reference for your pinned version.

Your plugin declares inject = ['tools', 'llm']. At runtime the operator replaces the LLM adapter plugin. What happens to your plugin?

        
    
          
  • Nothing; it keeps a reference to the old adapter until restart.
    • 
          
  • It is unloaded (all its registrations reverted) when the llm service disappears, and reloaded automatically when the new adapter provides it again.
    • 
          
  • It throws, because a required service was removed.
    • 
        

        
This is the spatial half of Cordis's composability. Declaring a dependency is a live contract, not a boot-time check: the kernel unloads dependents when a service goes away and reloads them when it returns. Combined with reversible effects, that is what makes hot-swapping a model adapter mid-session safe.

      

    


    

      
Deploying agents: SDK, headless and sub-agents

      
Python SDK

      
The SDK drives a bundled dsh --profile sdk runtime as a subprocess over newline-delimited JSON-RPC on stdio. It requires an explicit harness home and never silently reads ~/.dsh, which is exactly what you want in CI.


python -m venv .venv && . .venv/bin/activate
python -m pip install deepseek-harness-sdk      # pulls the matching runtime wheel
export DEEPSEEK_API_KEY=sk-...                  # DEEPSEEK_BASE_URL for a proxy


from pathlib import Path
from deepseek_harness import DeepSeekHarness

workspace = Path("./repo").resolve()
dsh_home  = Path("./.dsh-home").resolve()      # persistent profiles + sessions live here

with DeepSeekHarness(
    provider="deepseek-official",
    model="deepseek-v4-flash",
    max_tokens=49_152,
    cwd=str(workspace),
    dsh_home=str(dsh_home),
    profile="sdk-minimal",   # bash/pwsh + str_replace_editor, no compaction, JSONL sessions
) as harness:
    result = harness.run(
        "Inspect the repository and fix the failing tests.",
        session_id="ci-run-001",          # stable id => resumable, forkable
    )
    print(result.final_response)

      
The sdk-minimal profile is the benchmark configuration: a persistent shell, the editor, a 300-second shell timeout, a 16k-character editor output limit, and uncompressed JSONL session logs. To give the SDK agent more tools, install plugins into that profile and restart the runtime:


dsh plugin --profile sdk-minimal add file:/path/to/my-plugin-bundle
# or edit $DSH_HOME/profiles/sdk-minimal/cordis.patch.yml for persistent changes


      
Headless in a pipeline


# one-shot job; exits non-zero on config or boot failure
dsh --profile headless "Run the test suite, summarise failures, and propose a patch" > report.md

      
In a headless composition any tool that would prompt for approval is denied. Grant what the job needs in the profile's permission policy up front, and run it in a disposable container with the narrowest filesystem mode you can:

COPY dsh-home/ /dsh-home/            # profiles/headless with your patch + permission policy
ENTRYPOINT ["dsh", "--profile", "headless"]

Orchestrating other agents

      
Enable the sub-agent providers in your preset and the orchestrator can delegate to Claude Code, Codex, an ACP agent, or another dsh, and compare answers. The provider names are stable; the exact preset YAML keys were still moving during the alphas, so copy the shipped standard preset (apps/cli/config/agent-presets/standard/agent.cordis.yml) as your starting point.


# agent.cordis.yml (excerpt, shape illustrative)
- id: my-orchestrator
  name: dsh-preset
  config:
    prompt: ./PROMPT.md
    tools: [bash, str_replace_editor, web_search, subagent, send_message, todo]
    subagents:
      - subagent-claude-code        # Claude Agent SDK, inheritsParentContext: false
      - subagent-codex              # codex app-server --stdio
      - subagent-acp                # any Agent Client Protocol agent

      
Editors that speak the Agent Client Protocol (Zed, and the JetBrains and Neovim ACP clients) can drive dsh directly via dsh --profile acp. MCP servers are supported through the mcp family; the settings syntax was still shifting across releases, so verify it against the docs for your pinned version rather than a blog post.

You deploy a headless dsh job in CI. The agent tries to run a command your permission policy marks as "ask". What happens?

        
    
          
  • The job blocks waiting for an approval that never comes, until the shell timeout.
    • 
          
  • The call is denied: in a headless composition "ask" resolves to "deny" by design, because an unattended agent cannot approve itself.
    • 
          
  • The call runs, because headless mode disables the approval plane.
    • 
        

        
Neither hanging nor auto-approving is acceptable for automation, so dsh maps ask to deny when no human is attached. The operational consequence: whatever a CI job legitimately needs must be allowed explicitly in the profile's policy, and everything else should be denied rather than left as ask.

      

    


    

      
Where people go wrong

      
Pitfall
        
Treating a preview as a platform. The README shouts that there will be compatibility-breaking changes; one release candidate moved twice in a week, and v0.1.3-alpha.1 already broke the session persistence API. Pin the exact version everywhere and keep a rollback path.

      
Pitfall
        
Assuming the sandbox isolates the agent. It confines filesystem effects only. Network, processes and credentials in the environment are all reachable in every mode. The SAFETY notice recommends disposable VMs or containers, minimal privileges, and backups. A day-two fix closed a /proc/<pid>/root escape, which tells you the surface is still being explored.

      
Pitfall
        
Installing plugins on trust. Plugins are arbitrary TypeScript with access to everything the process has. The dsh-plugin GitHub topic is a discovery mechanism, not a security certification. Read the code, install into a test profile first, and restart after profile changes (a missing tool after install is usually a stale process).

      
Pitfall
        
Reaching for the cordis preset by default. It hands the model JavaScript execution against the live process. It is a creator tool for building presets, and it is deliberately not selected unless you choose it.

      
Pitfall
        
Reading benchmark numbers as model numbers. DeepSeek's V4-Pro agent results were measured with dsh in minimal mode. They are model-plus-harness numbers, which is the honest way to measure, but it means comparisons against other vendors' harnesses are not apples to apples.

      
Pitfall
        
Budgeting on the old API prices. DeepSeek moved to peak / off-peak pricing on 16 August 2026, roughly doubling standard rates and raising cached-input prices by more than tenfold. Still cheap relative to frontier competitors, but re-run the numbers.

      
Smaller gotchas: GitHub Issues are disabled (bugs go to Discussions or Discord); the narrowest sandbox mode is not in any shipped preset, so you compose it yourself; and the web UI is the only fully interactive surface, with no hosted background-agent service like Claude Code or Codex offer.
