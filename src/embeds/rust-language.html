Rust — Why It Exists, What It Costs, and Where It's Used

You keep seeing Rust everywhere — inside the Linux kernel, under AWS Lambda, and quietly powering the Python tools you already use (uv, ruff). The one idea

Most languages pick one of two deals for managing memory. Rust invented a third.

  • Manual (C/C++): you free() memory yourself. Maximum speed, but a mistake means a use-after-free, double-free, or buffer overflow — the bugs behind most security CVEs.
  • Garbage collected (Java/Go/Python/JS): a runtime frees memory for you. Safe and easy, but you pay with a background collector — pauses, latency spikes, and memory overhead you don't control.
  • Rust's third deal — ownership: the compiler proves, at build time, exactly when every value is no longer used and frees it there. No manual free. No garbage collector. No runtime cost.

The mechanism that makes this possible is a set of rules the compiler enforces — the borrow checker. It's the thing beginners "fight" and experts stop noticing. Everything distinctive about Rust — the safety, the speed, the learning curve — flows from this one design choice.

Key insight

Rust moves the work a garbage collector does at runtime to something the compiler does at compile time. The safety is free at runtime because it was already paid for during cargo build. That single trade is the whole language in one sentence.

How ownership works

Three rules, and everything else follows:

  1. Every value has exactly one owner (a variable).
  2. When the owner goes out of scope, the value is dropped (its memory freed) — automatically.
  3. You can borrow a reference to a value instead of taking ownership — under one rule below.

Move semantics

Assigning a heap-owning value doesn't copy it — it moves ownership. The old name becomes unusable, which is how Rust guarantees a value is freed exactly once.

// A String owns a heap buffer.
let s1 = String::from("hello");
let s2 = s1;            // ownership MOVES from s1 → s2
// println!("{s1}");    // ❌ compile error: borrow of moved value `s1`
println!("{s2}");       // ✅ prints: hello

// A plain integer is `Copy` — cheap, stack-only — so it duplicates instead:
let a = 5;
let b = a;              // a is COPIED, not moved
println!("{a} {b}");     // ✅ prints: 5 5

The borrowing rule (the whole borrow checker, compressed)

The rule

At any moment, a value may have either any number of shared references (&T, read-only) or exactly one exclusive reference (&mut T, read-write) — never both at once. "Many readers XOR one writer."

That one rule eliminates data races by construction: if only one thing can write at a time and nothing else can even read while it does, there is no race to have.

fn main() {
    let mut v = vec![1, 2, 3];
    let first = &v[0];     // shared borrow of v begins
    v.push(4);             // ❌ needs &mut v while `first` is alive
    println!("{first}");
}
// error[E0502]: cannot borrow `v` as mutable because
//               it is also borrowed as immutable

This looks annoying until you realize what it prevented: v.push(4) can trigger the vector to reallocate its buffer, which would leave first pointing at freed memory. In C++ this compiles happily and is a real, shipped class of bug (iterator invalidation → dangling pointer). Rust rejects it before the program ever runs.

Deep dive — lifetimes & non-lexical lifetimes (hidden in Skim mode)

References carry an invisible lifetime: a compile-time proof that the referent outlives the reference. Usually the compiler infers them, but sometimes you annotate: fn longest<'a>(x: &'a str, y: &'a str) -> &'a str says "the returned reference lives at least as long as both inputs." Lifetimes are not runtime objects — they're erased after checking, exactly like the borrow rules.

Since 2018, Rust uses non-lexical lifetimes (NLL): a borrow ends at its last use, not at the closing brace. That's why the animation below can take a &mut right after the last read of the shared borrows — they're already considered dead. NLL is what made the borrow checker go from "constantly in your way" to "usually invisible."

Why does let s2 = s1; make s1 unusable for a String, but let b = a; leaves a perfectly usable for an i32?

  • Because String is mutable and i32 is not
  • Because String owns a heap buffer, so it's moved (to guarantee the buffer is freed once); i32 is a cheap stack value that implements Copy, so it's duplicated
  • Because integers are global and strings are local
Move vs. copy is about ownership of a resource, not mutability. Types that own something on the heap (String, Vec, Box) move on assignment so exactly one owner is responsible for freeing it — this is how Rust rules out double-frees. Small, self-contained stack types (i32, bool, char) implement the Copy trait and are bit-copied instead, so the original stays valid.

Pros and cons, with the code that shows them

What Rust buys you

1 · Memory safety with zero runtime cost. The whole first section — no GC, no manual free, no dangling pointers, checked at build time. This is the headline, and it's why the US White House's 2024 cybersecurity directive names Rust as a memory-safe language to migrate toward.

2 · No null — absence is a value you must handle. Rust has no null pointers. "Might be missing" is modeled by Option<T>, and the compiler won't let you use the inner value without checking. Tony Hoare called null his "billion-dollar mistake"; Rust simply doesn't have it.

fn first_char(s: &str) -> Option<char> {
    s.chars().next()          // Some(c) if non-empty, else None
}

fn main() {
    match first_char("hi") {
        Some(c) => println!("first: {c}"),  // first: h
        None    => println!("empty string"),
    }
}

3 · Errors are values, not surprises. No exceptions. Fallible functions return Result<T, E>, and the ? operator propagates failures without ceremony. The type signature tells you what can go wrong.

use std::num::ParseIntError;

fn double(input: &str) -> Result<i32, ParseIntError> {
    let n: i32 = input.parse()?;   // `?` returns Err early on failure
    Ok(n * 2)
}

fn main() {
    println!("{:?}", double("21"));   // Ok(42)
    println!("{:?}", double("oops")); // Err(ParseIntError { .. })
}

4 · Fearless concurrency. The same borrow rules that stop dangling pointers also stop data races — across threads. Sharing mutable state without a lock simply won't compile.

use std::{thread, sync::{Arc, Mutex}};

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];
    for _ in 0..10 {
        let c = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            *c.lock().unwrap() += 1;    // lock → safe mutation
        }));
    }
    for h in handles { h.join().unwrap(); }
    println!("{}", *counter.lock().unwrap()); // 10, deterministically
}

Drop the Mutex and try to share &mut across threads and the compiler stops you by the Send/Sync traits. The data race is a type error.

5 · Zero-cost abstractions + first-class tooling. Generics and traits monomorphize to code as fast as hand-written specializations. And cargo (build + package manager + test runner), clippy (linter), rustfmt, and crates.io ship as one coherent story — consistently the most-loved toolchain in developer surveys.

What Rust charges you

1 · A real learning curve. The borrow checker rejects programs that "obviously work" until ownership clicks. Expect a few weeks of friction. New Rustaceans often escape by cloning everything:

// Beginner reflex: clone to make the borrow checker quiet.
fn process(data: &Vec<String>) -> Vec<String> {
    data.clone()               // copies the WHOLE vector — a smell in a hot path
        .into_iter()
        .map(|s| s.to_uppercase())
        .collect()
}
// Idiomatic: borrow, don't clone — iterate over &data directly.

2 · Slow compiles. All that checking and monomorphization has a price: build times are Rust's most common real complaint, especially on large projects.

3 · Verbosity & time-to-prototype. Explicit types, error handling, and lifetimes mean more code up front than Python or Go. For a throwaway script, that's a bad trade.

4 · Async is genuinely complex. async/await works, but drags in Send bounds, Pin, and "function coloring." The 2024 edition and libraries like axum 0.8 keep smoothing it, but it's still the steepest part of the ecosystem.

5 · Younger ecosystem in some domains. GUI, game engines, and some enterprise niches are less mature than the C++/Java/C# equivalents — improving fast, but not always there yet.

Honest take

Rust is a phenomenal fit when correctness under performance pressure matters: infrastructure, systems, hot paths, anything where a GC pause or a memory bug is expensive. It's often the wrong tool for glue scripts, quick prototypes, or CRUD apps where a GC is a non-issue and developer speed wins — there, Python or Go frequently beat it.

Pattern to notice
        
If you work in ML or platform, you're already shipping Rust. uv, ruff, polars, and HuggingFace tokenizers are Rust cores wrapped in Python. The most common industrial use of Rust isn't rewriting your app — it's replacing the hot 5% that Python or a GC can't make fast enough.

The service was fast enough on average in Go, but Go's garbage collector introduced recurring latency spikes every couple of minutes as it scanned memory. Rust has no GC, so those pauses disappeared and tail latency flattened — the win was predictability, not raw average throughput. (Go handles concurrency very well; that was never the issue.)

      

    


    

      
Starter projects — a ladder, not a list

      
Reading Rust doesn't teach Rust; the borrow checker does. Build in this order — each rung forces a specific concept. Start every one with cargo new <name>.


      
Rung 1 — Guessing game ~1 hour

      
The canonical first program (Chapter 2 of The Book). A number-guessing loop.
Teaches: cargo, adding a crate (rand), match, Result, and the read-parse-loop shape. Do this to get the toolchain under your fingers.


      
Rung 2 — A CLI tool a weekend

      
Build a real command-line tool: a grep clone (the Book's minigrep), a word-frequency counter, or a small todo manager with a JSON file.
Teaches: ownership across function boundaries, &str vs String, iterators, file I/O, error handling with ?, and argument parsing with clap. This is where ownership finally clicks.


      
Rung 3 — A parser or tiny interpreter a week

      
A calculator that parses 2 + 3 * 4, or a JSON/CSV parser, or a mini Lisp.
Teaches: the crown jewels of Rust's type system — enums as sum types, exhaustive match, recursion with Box, and how "make illegal states unrepresentable" feels. This is the project that makes people fall in love with the language.


      
Rung 4 — An HTTP JSON API a week+

      
A small web service with axum + tokio + serde — a URL shortener or a notes API backed by SQLite (sqlx).
Teaches: async/await, traits, JSON (de)serialization, and shared state (Arc) — the realistic backend shape, and your first honest taste of async's complexity.


      

        
Deep dive — the highest-leverage project for a Python/ML person (Skim hides this)

        
Rung 5 — A Python extension in Rust

        
Take a hot function from your own Python code, rewrite it in Rust with PyO3, and build it into an importable wheel with maturin. pip install it, import it, watch a hot loop get 10–50× faster.

        
Teaches: the actual industrial workflow — you don't rewrite the app, you replace the bottleneck. This is exactly how polars, tokenizers, and pydantic-core are built, and it's the fastest way for Rust to earn its keep on a team that already ships Python.

      


      
How to actually learn it
        
Work through The Rust Book and Rustlings in parallel with Rungs 1–2, not before them. And run cargo clippy constantly — it teaches idiomatic Rust by correcting you, which beats memorizing rules.

    


    

      
Where people go wrong

      
Pitfall 1 · Cloning to silence the checker
        
When a borrow error appears, the reflex is .clone(). It compiles, but you've copied data — sometimes a lot — to dodge a message that was usually pointing at a real aliasing problem. Fix: restructure so there's one clear owner and pass & references. Clone deliberately, not defensively.

      
Pitfall 2 · Reaching for Rc<RefCell<T>> or unsafe too early
        
RefCell moves borrow checking from compile time to runtime — trading a compile error for a potential panic. unsafe throws the guarantees away entirely. Both are real tools, but if you're using them to escape the borrow checker in week one, you're fighting the language instead of learning it.

      
Pitfall 3 · Assuming you need async
        
async is for high-concurrency I/O (thousands of simultaneous connections). A CLI tool, a parser, or a batch job is simpler, faster to write, and often just as fast written synchronously. Don't pay async's complexity tax until the workload asks for it.

      
Pitfall 4 · .unwrap() everywhere
        
Fine in a prototype or a test; in production it's a landmine — every unwrap is a panic waiting for the wrong input. Once past prototyping, propagate with ? and handle errors at the edges.

      
Pitfall 5 · "The borrow checker makes it slow"
        
A common misconception. Every ownership and borrow rule is enforced at compile time and erased before codegen. There is zero runtime cost — the checking made your build slower, not your program.
